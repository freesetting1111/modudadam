# 커뮤니티 대용량 구조

## 게시판 테이블 전략

카테고리마다 게시글 테이블을 만들지 않고 `posts` 단일 테이블을 유지합니다. 게시판은 `category_id`로 구분합니다.

- 공통 기능(검색, 신고, 댓글, 스크랩, 관리자 조회)을 한 쿼리와 한 데이터 모델로 유지할 수 있습니다.
- 카테고리 추가가 DDL 변경이나 신규 API 구현으로 이어지지 않습니다.
- 카테고리와 정렬 키가 포함된 부분 인덱스로 특정 게시판만 빠르게 읽을 수 있습니다.
- 테이블 분리는 보관 정책·컬럼·권한·트랜잭션 흐름이 완전히 다른 콘텐츠에만 사용합니다.

`018_post_feed_scale.sql`은 다음을 적용합니다.

- 최신순 전체/카테고리 피드 복합 인덱스
- 인기순 카테고리 피드 복합 인덱스
- 한글 부분 검색을 위한 `pg_trgm` GIN 인덱스
- 사용자별 미연결 이미지 정리 인덱스

## 페이지네이션

`OFFSET`은 뒤 페이지로 갈수록 버려야 하는 행이 늘어납니다. 게시글 API는 정렬 키를 담은 불투명 커서를 반환하며 프런트엔드는 이 커서로 다음 20개를 요청합니다.

최신순 커서:

```text
is_pinned, published_at, id
```

인기순 커서:

```text
is_pinned, popularity_score, published_at, id
```

## 추가 확장 시점

- 게시글이 수천만 건을 넘어 인덱스 유지 비용이 커질 때 월/분기 단위 `published_at` 파티셔닝을 검토합니다.
- 조회수가 매우 높은 글에서 단일 행 갱신 경합이 보이면 조회 이벤트를 Redis/큐에 모아 배치 반영합니다.
- 검색 조건과 랭킹이 복잡해지면 OpenSearch 같은 별도 검색 인덱스를 도입합니다.
- 이미지 트래픽이 커지면 S3 앞에 CloudFront를 붙이고 `AWS_S3_PUBLIC_BASE_URL`에 배포 도메인을 설정합니다.
